# Database

## Core Tables

`projects`, `scholarship_holders`, `scholarships`, `funding_releases`, `monitoramento`, `dashboard_settings`, `app_users`, `user_projects`. Plus `audit_logs` para rastreamento global de mudanças, e o stack Plano de Trabalho/Balancete (`planos_trabalho`, `plano_rubricas`, `plano_desembolsos`, `rubricas`, `balancetes`, `balancete_lancamentos`, `conta_rubrica_map`, `reconciliacoes`). All core tables use UUIDs with `updated_at` auto-triggers, except `dashboard_settings` and `audit_logs`. RLS is enabled on all tables — anonymous users see nothing. **Desde a migração 033 o RLS é escopado por usuário** (multi-tenancy por centro de custo): `app_users` define o papel (admin/professor) e `user_projects` os centros de custo permitidos; as policies usam `is_admin() or project_id = any(allowed_project_ids())`. Antes da 033 o RLS era permissivo (`using (true)`) — seguro apenas porque o signup público está desativado no Supabase (só e-mails pré-autorizados entram).

## Notable Schema Details

- **External scholarships** (migration 008): `scholarships.project_id` is nullable. When NULL, `funding_source` text column identifies the external source (e.g., "CIAMB"). View `v_scholarship_timeline` shows "Externa: {source}" as project name.
- **Cascade deletes reverted** (migration 022): FKs from scholarships, funding_releases, and expenses to projects originally used `ON DELETE CASCADE` (migration 007). This was reverted to `ON DELETE RESTRICT` (migration 022) to prevent catastrophic accidental deletion of historical financial data. Projects must be "inactivated" instead of deleted.
- **Dynamic balance** (migrations 009-011): `projects.balance_date` records when the initial balance was reported. The `calc_project_monthly()` RPC accepts `p_balance_status` to control current-month payment logic. `calc_projects_batch()` is a batch variant that eliminates N+1 queries on the dashboard.
- **Editor mode save** (migration 012): `save_editor_changes()` applies deletes/updates/inserts to scholarships in a single transaction, then logs the operation in `scholarship_audit`.
- **Portuguese months + batch alerts + stats** (migration 013): `fmt_month_pt()` replaces `to_char` locale-dependent month labels. Adds `get_alerts_for_projects()` for N+1-free dashboard alerts, plus `funding_stats()` and `expenses_stats()` RPCs for CrudPage stats cards.
- **Audit invalid data** (migration 014): Diagnostic SELECT queries to find records with invalid values (amount <= 0, inverted dates). Run before migration 015 to inspect problems before constraints are applied.
- **Check constraints** (migration 015): Removes invalid records, adds `CHECK` constraints for positive monetary values (`amount > 0`) and date ordering (`start_date < end_date`) on `scholarships`, `funding_releases`, `expenses`, and `projects`.
- **Save project RPC** (migration 016): `save_project()` creates or updates a project and its `dashboard_settings` entry in a single transaction, preventing inconsistent state if one of the two operations fails.
- **Project balances history** (migration 017): `project_balances` table stores monthly balance snapshots per project. Triggers `trg_sync_project_balance` and `trg_balances_updated_at` keep `projects.initial_balance`, `yield_amount`, and `balance_date` in sync with the most recent balance row. RPCs: `upsert_project_balance()` and `get_balances_for_month()`.
- **Integrity fixes** (migration 021): `sync_holder_active` now checks `start_date <= current_date` (not just `end_date >= current_date`), so future-dated scholarships no longer mark a holder as active. `sync_project_balance` now handles DELETE — when a balance row is deleted, `projects` is updated from the remaining latest row (or zeroed if none left).
- **Global Audit Triggers** (migration 023): A centralized `audit_logs` table replaces the partial `scholarship_audit`. PostgreSQL triggers automatically log `INSERT`, `UPDATE`, and `DELETE` actions for `projects`, `scholarship_holders`, `scholarships`, `funding_releases`, and `expenses`, capturing `old_data`, `new_data`, and `performed_by`.
- **project_balances RESTRICT** (migration 024): Alinha a FK de `project_balances.project_id` ao mesmo `ON DELETE RESTRICT` das demais tabelas financeiras (ver migração 022). Política do projeto: projetos **nunca são excluídos**, apenas inativados via campo `active`. Migrações 022 e 024 implementam RESTRICT como defesa em profundidade — qualquer tentativa de `DELETE` em `projects` com registros associados falha com FK violation, forçando o fluxo de inativação.
- **Plano de Trabalho** (migration 025): Adiciona 4 tabelas: `rubricas` (catálogo fixo com 16 códigos: a-g, sub-rubricas de Pessoal, cip_ufg, cip_ua, dao), `planos_trabalho` (cabeçalho versionado por projeto — versao=0 original, 1+ remanejamento), `plano_rubricas` (valor previsto por rubrica em cada versão, com `descricao_livre` para sub-itens variáveis de b/e/f), `plano_desembolsos` (cronograma da Seção II.b). Índice parcial `uq_plano_ativo_por_projeto` + trigger `enforce_single_plano_ativo` garantem apenas 1 versão ativa por projeto. Cria também o bucket de Storage `plano-trabalho-docs` (privado, autenticado), e a coluna `projects.funape_managed` (preparação para Fase 2 — Balancete). `save_project()` ganha o parâmetro `p_funape_managed`.
- **Balancete** (migration 026): Adiciona 3 tabelas: `balancetes` (cabeçalho de cada PDF importado — data_referencia, saldo_disponivel, rendimento_liquido, totais), `balancete_lancamentos` (linhas contábeis 7.1.3.x com `rubrica_code` resolvido automaticamente pelo trigger `trg_auto_resolve_rubrica`), `conta_rubrica_map` (mapeamento prefix-based de contas FUNAPE → rubricas, com seed inicial para 7.1.3.02 → 'd', 7.1.3.04 → 'a.bolsas', 7.1.3.05.01.99520 → 'cip_ua', etc.). Função `resolve_rubrica_for_conta()` faz longest-prefix-match. Cria o bucket Storage `balancete-pdfs`. **Política FUNAPE**: deleta `expenses` de projetos `funape_managed=true` (one-time) e instala trigger `block_expenses_for_funape` que bloqueia novos inserts/updates em `expenses` para esses projetos (erro com SQLSTATE 23514). `get_previsto_vs_realizado(p_project_id)` cruza o plano ativo com o balancete mais recente, agregando previsto/realizado/saldo/percentual por rubrica.
- **Conta-rubrica audit + cadastro inline** (migration 027): Seeds adicionais ao `conta_rubrica_map` descobertos na auditoria de 4 balancetes reais — `7.1.3.05.01.00062 → cip_ufg` (FUNDO INSTITUCIONAL sem CIP no nome), `7.1.3.20 → f` (EQUIPAMENTOS / Investimento), `7.1.3.01.01 → a.colab` (ORDENADOS E SALARIOS), `7.1.3.01.02 → a.enc` (ENCARGOS S/ CLT), `7.1.3.01.03 → a.colab` (BENEFÍCIOS SOCIAIS). Estende `upsert_balancete(p_payload)` para aceitar `new_mappings: [{ conta_prefix, rubrica_code, descricao }]` opcional — inseridos em `conta_rubrica_map` ANTES dos lançamentos, de modo que o trigger auto-resolve já enxergue o mapeamento. Isso permite que a UI de revisão do balancete (modal split-view) cadastre mapeamentos pontuais para códigos novos sem trip ao banco a parte. Códigos `7.1.3.60.01.*` (IR/IOF s/ aplicação) e `7.1.3.62.01.*` (IOF s/ recebimento) ficam **intencionalmente não-mapeados** — tributos sobre rendimento financeiro não pertencem ao plano de trabalho.
- **Reconciliação de Bolsas** (migration 028): Adiciona `cpf` (text, 11 dígitos apenas numéricos, `unique`, normalizado via `regexp_replace`) e `education_level` (text — "Formação" do FUNAPE) em `scholarship_holders`, e `scholarship_type` (text — "Tipo" do FUNAPE, ex.: "COM VINCULAÇÃO IFES (FIXO)") em `scholarships`. `cpf` é nullable (registros anteriores ao fluxo de reconciliação). Cria o índice parcial `idx_holders_cpf` (`where cpf is not null`) e a RPC `apply_reconciliation(p_project_id, p_actions jsonb)` — aplica as mudanças aprovadas na revisão (creates/updates/ends numa transação) e loga em `scholarship_audit` com `action='reconciliation'`.
- **Reconciliação global + merge de duplicados** (migration 029): Reescreve `apply_reconciliation` para resolver pessoas contra o universo **global** de holders (não só o projeto selecionado): `creates` aceita `holder_id` (vincula nova bolsa a holder existente, evitando duplicado, com backfill de cpf/e-mail/formação e **nome da planilha FUNAPE como fonte da verdade**), faz upsert por `cpf` (`on conflict` reusa o holder) quando só o CPF bate, ou cria holder novo. Adiciona `merge_holders(p_canonical_id, p_duplicate_ids uuid[])` — repointa as bolsas dos duplicados para o canônico, consolida cpf/e-mail/formação/ativo (canônico tem precedência; nulos preenchidos a partir dos duplicados), remove os duplicados ANTES de gravar o cpf consolidado (para não violar a `unique` transitoriamente) e loga em `scholarship_audit` com `action='merge_holders'`.
- **Exclusão em cascata consciente** (migration 030): RPC `delete_holder_cascade(p_holder_id)` — remove as bolsas vinculadas e o bolsista numa única transação. Dá uma saída deliberada ao `ON DELETE RESTRICT` das FKs (022/024) para casos legítimos como duplicatas: a tela de Bolsistas avisa o usuário, mostra a contagem de bolsas e só após confirmação explícita chama esta função. O RESTRICT no banco continua intacto como rede de segurança; as exclusões são registradas em `audit_logs` pelo trigger da migração 023. `security invoker` (não `definer`) — roda com os privilégios do chamador.
- **Multi-tenancy por centro de custo** (migration 033): Adiciona `app_users` (papel `admin`/`professor`, PK `user_id` → `auth.users`, 1:1) e `user_projects` (centros de custo permitidos por usuário, PK composta `user_id`+`project_id`). Helpers `is_admin()`, `allowed_project_ids()`, `assert_project_allowed(p_project_id)` — todos `security definer set search_path = public, pg_temp` (`is_admin`/`allowed_project_ids` **precisam** ser definer: recursariam infinitamente nas policies de `app_users`/`user_projects` se fossem invoker). Trigger `on_auth_user_created` em `auth.users` auto-cria a linha em `app_users` (papel `professor`, nome = `split_part(email,'@',1)`) no cadastro de novo auth user. Substitui todas as policies permissivas por escopadas: tabelas-filhas com `project_id` (`scholarships`, `funding_releases`, `monitoramento`, `project_balances`, `balancetes`, `planos_trabalho`, `reconciliacoes`) usam `is_admin() or project_id = any(allowed_project_ids())`; `projects` CRUD é admin-only; `scholarship_holders` ganha `created_by uuid` + trigger `set_holder_created_by` (SELECT/UPDATE por admin, holder criador, ou via bolsa num projeto permitido; DELETE só admin ou criador sem bolsas — o `ON DELETE RESTRICT` das FKs é a rede de segurança); `balancete_lancamentos`/`plano_rubricas`/`plano_desembolsos` (sem `project_id` direto) ficam admin-only (professores acessam via RPCs guardadas); `audit_logs` SELECT vira admin-only (corrige vazamento — antes qualquer autenticado lia a trilha inteira). Backfill: Laerte/Victor = admin, demais = professor.

- **Estender o professor** (migration 034): Aditiva sobre a 033. `save_project` deixa de ser admin-only — admin cria/edita qualquer; professor cria (auto-atribui a si em `user_projects`) e edita só os seus (`assert_project_allowed`), com checagem de cadastro em `app_users` (defesa contra desativação por remoção de linha). `apply_reconciliation` troca o guard admin-only por `assert_project_allowed(p_project_id)` **e** escopa as 3 mutações de `scholarship_holders` — reusa o holder (dedup preservado) mas só muta campos de holders dominados pelo chamador (admin, ou `created_by = auth.uid()`, ou com bolsa no `p_project_id`); corrige o `full_name = excluded.full_name` incondicional da 033 (zerava o nome com `nome=''`). Policy de INSERT em `reconciliacoes` vira escopada (`is_admin() or project_id = any(allowed_project_ids())`) — o handler de bolsas registra a reconciliação direto. `merge_holders` e `save_user_assignments` continuam admin-only.

- **Saldo livre / camada de decisão** (migration 038): Adiciona `get_saldo_livre(p_project_id)`, a primeira RPC de **decisão** (as demais são leitura/cadastro). Cruza as duas metades que já existiam mas nunca se falavam: o retrospectivo (`get_previsto_vs_realizado`) e o prospectivo (`calc_project_monthly`). Fórmula: `saldo_livre = previsto − realizado − compromissos até o fim da vigência`. Compromissos contam do mês **seguinte** ao balancete (o anterior já está no `realizado`); balancete atrasado deixa o número conservador, com o atraso em `balancete_defasagem_meses`. Devolve `grupos` (rollup por `coalesce(parent_code, code)` — a superfície de decisão, porque o plano ora orça na letra-mãe ora na sub-rubrica) e `rubricas` (detalhe), além de `bolsas_ativas` (por pessoa, sem CPF), `meses_restantes` e `avisos`. Cada grupo carrega `compromissos_cobertura` (`'bolsas'` | `'nenhuma'`): só bolsas têm compromisso futuro rastreável no banco, então onde é `'nenhuma'` o `saldo_livre` é apenas `previsto − realizado` e **não** foi verificado. Não considera remanejamento entre letras. Ver o cabeçalho da migração para a semântica completa.

- **Simulação de alocação** (migration 039): Adiciona `simular_alocacao(p_tipo, p_valor, p_rubrica, p_inicio, p_meses, p_project_ids)`, a segunda RPC de decisão. A 038 responde "quanto está livre **neste** centro de custo?"; a 039 responde a comparativa ("onde é melhor colocar uma bolsa de R$ 2.000/mês?"), rodando `get_saldo_livre` em todos os centros visíveis ao chamador. Herda a semântica da 038 e não redefine nada. **É shortlist com justificativa, não decisão:** ordena por urgência de gasto e não julga mérito — se um bolsista se justifica dentro do objeto de um projeto não existe em tabela alguma. Avalia **três restrições independentes** (orçamento, caixa e prazo), cada item traz `motivo_codigo` (`prazo`/`caixa`/`orcamento`/`sem_rubrica_pessoal`/`sem_plano_ativo`) dizendo qual está amarrando, e **todos os itens têm o mesmo conjunto de chaves**, inclusive os de curto-circuito, para tela e MCP iterarem sem checar forma. Ranking por risco de devolução (`saldo_livre_realocavel / meses_restantes`), com `cabe` e `cabe_parcial` no mesmo balde. `risco_devolucao.base` (`balancete` | `apenas_plano`) e o alerta em `resumo.observacao` sinalizam quando a ordem está sendo produzida por **falta de dado** — sem balancete o realizado é zero por ausência, não por execução, e o centro sobe ao topo indevidamente. `security invoker` (ao contrário da 038): tudo que lê direto já é escopado por RLS, e o dado admin-only chega pela `get_saldo_livre`, que é definer e guardada. Ver o cabeçalho da migração para as decisões de semântica.

  > ⚠️ **Divergência conhecida na `nota` da 039** (aberta em 2026-08-12). O código usa `coalesce(v_defasagem, 0) <= 2` para `caixa.cobertura = 'atualizada'` (039, linha ~811), e o comentário ao lado diz 2 meses. Mas a string `nota` — o campo que o **modelo lê e repete ao usuário** — afirma *"'atualizada' quando é no máximo 1 mês"*. O comportamento correto é 2; só o texto está errado, e é justamente o texto que vira frase na tela. A 040 seguiu o **código** (2 meses) para panorama e simulação concordarem. Corrigir exige recriar `simular_alocacao` inteira numa migração nova, porque não há como alterar só a string.

  > ⚠️ **Lacuna conhecida na 038 no caminho sem plano** (aberta em 2026-08-12). Quando não há plano ativo, `get_saldo_livre` retorna um objeto curto com `has_balancete` mas **sem** `data_referencia` nem `balancete_defasagem_meses` — embora já tenha consultado os dois antes do curto-circuito. Foi o que obrigou a 040 a criar o estado `caixa.cobertura = 'desconhecida'`: sem ele, `coalesce(defasagem, 0) <= 2` leria NULL como zero e declararia "em dia" um balancete de idade desconhecida. Incluir esses dois campos no caminho curto da 038 elimina o quarto estado.

- **Panorama + reparo dos alertas** (migration 040): Duas coisas, descobertas uma pela outra. **(A) Reparo:** `get_project_alerts` estava **quebrada em runtime desde a 032**. O corpo vivo no banco era o da migração 003, com um quarto alerta (`expense_no_description`) lendo `public.expenses`; a 032 dropou essa tabela **e** recriou a função sem esse alerta, mas só o drop chegou ao banco. Como plpgsql resolve nome de tabela apenas em tempo de **execução**, a função seguiu existindo e só falhava quando alguém pedia alerta — derrubando os alertas da página Projetos (`projetos.js:138`) e o sino do Dashboard (`dashboard.js:213`, via `get_alerts_for_projects`). Já constava como Crítico #2 do [`historico/bug-hunt-2026-07-16.md`](historico/bug-hunt-2026-07-16.md) e ficou aberto até aqui; foi redescoberto porque `get_panorama` chama a função e explodiu na primeira execução. A 040 reaplica textualmente a versão da 032. Varredura no schema confirmou que a 4.5 foi a **única** seção da 032 que não chegou ao banco. **(B) `get_panorama(p_project_ids, p_incluir_inativos)`**, a terceira RPC de decisão: a 038 responde "quanto está livre **neste** centro?", a 039 "onde colocar **este** gasto", e nenhuma respondia "como estão os projetos?" — que é a pergunta anterior às duas e a primeira de quem coordena vários centros. **Descreve, não ranqueia:** ordem alfabética, sem significado; ranquear é da 039, que parte de uma hipótese concreta de gasto, e um segundo ranking aqui usaria outro critério e produziria listas discordantes. **Não recalcula nada** — todo número vem de `get_saldo_livre`, `get_project_alerts` ou `v_project_summary`. ## Server-Side Functions (RPC)

- `calc_project_monthly(p_project_id, p_start_date, p_end_date, p_balance_status)` — monthly projection per project (labels in pt-BR via `fmt_month_pt`)
- `calc_projects_batch(p_project_ids[], p_start_date, p_balance_status)` — batch version for dashboard
- `calc_general_dashboard(p_start_date, p_end_date, p_balance_status)` — consolidated KPIs across included projects
- `get_project_alerts(p_project_id)` — alert rules for one project (bolsa excedendo a vigência, saldo negativo projetado, projeto sem vigência). **Reaplicada pela mig. 040**: o corpo da 003, que lia a tabela `expenses` dropada pela 032, ficou vivo no banco e quebrava em runtime — plpgsql só resolve nome de tabela ao executar, então a função existia e só falhava quando chamada.
- `get_alerts_for_projects(p_project_ids[])` — batch alerts for multiple projects (chama a de cima em laço; quebrava junto e foi consertada junto)
- `save_editor_changes(p_project_id, p_deletes, p_updates, p_inserts)` — transactional save of editor mode changes with audit log
- `save_project(p_name, p_id, ...)` — upsert project + dashboard_settings in single transaction. **Desde a mig. 034 não é mais admin-only**: admin cria/edita qualquer; professor cria (auto-atribui a si em `user_projects`) e edita só os seus (`assert_project_allowed`), com checagem de cadastro em `app_users` (defesa contra desativação por remoção de linha).
- `upsert_project_balance(p_project_id, p_reference_month, p_reference_year, p_initial_balance, p_yield_amount, p_balance_date, p_notes)` — insert or update a monthly balance row; triggers `sync_project_balance`
- `get_balances_for_month(p_month, p_year)` — returns all projects with their balance for the given month; projects without a balance row have null fields
- `funding_stats()` — aggregated funding totals `{total, count}`
- `monitoramento_stats()` — contagem de observações `{count}` (mig. 032; substituiu `expenses_stats()`, dropada junto com a tabela `expenses`)
- `fmt_month_pt(date)` — returns Portuguese month label (e.g., "Mai/26")
- `upsert_plano_trabalho(p_payload jsonb)` — cria/atualiza uma versão do Plano de Trabalho a partir do JSON revisado (transacional: cabeçalho + rubricas + desembolsos). Calcula `versao = MAX(versao) + 1` em inserções.
- `ativar_plano_trabalho(p_plano_id uuid)` — marca uma versão como a ativa (trigger desativa as demais).
- `get_plano_ativo(p_project_id uuid) → jsonb` — retorna a versão ativa com `rubricas` e `desembolsos` embutidos.
- `get_planos_historico(p_project_id uuid) → table` — lista resumida (sem rubricas) das versões em ordem `versao desc`.
- `upsert_balancete(p_payload jsonb)` — cria/atualiza um balancete e substitui seus lançamentos. `rubrica_code` é setado automaticamente pelo trigger.
- `get_balancetes_by_project(p_project_id uuid) → table` — lista dos balancetes do projeto em ordem `data_referencia desc`.
- `get_balancete_detalhado(p_balancete_id uuid) → jsonb` — cabeçalho + lançamentos (com nome da rubrica resolvido).
- `get_previsto_vs_realizado(p_project_id uuid) → jsonb` — cruza plano ativo + balancete mais recente. Retorna `{ has_plano, has_balancete, balancete_id, data_referencia, saldo_disponivel, rendimento_liquido, rubricas: [{rubrica_code, rubrica_name, previsto, realizado, saldo, perc_executado}], nao_mapeados: [{conta_codigo, ...}] }`.
- `resolve_rubrica_for_conta(p_conta text) → text` — utility: longest-prefix-match de conta contábil → rubrica via `conta_rubrica_map`.
- `apply_reconciliation(p_project_id uuid, p_actions jsonb) → integer` — aplica a reconciliação de bolsas aprovada na revisão. `p_actions = { creates, updates, ends }`. `creates` aceita `holder_id` (vincula a holder existente, com backfill e nome FUNAPE como fonte da verdade), upsert por CPF, ou cria holder novo. `updates` altera bolsa + backfill do holder (cpf/full_name/education_level). `ends` encerra bolsas removidas (`status='ended'`). Loga em `scholarship_audit` (`action='reconciliation'`). Retorna o total de alterações. **Desde a mig. 034 não é mais admin-only**: guard `assert_project_allowed(p_project_id)` (admin ou projetos do chamador) e as 3 mutações de `scholarship_holders` são escopadas — reusa holder alheio (dedup) mas só muta campos de holders dominados pelo chamador (admin, ou `created_by = auth.uid()`, ou com bolsa no `p_project_id`).
- `merge_holders(p_canonical_id uuid, p_duplicate_ids uuid[]) → integer` — mescla bolsistas duplicados no canônico: repointa as bolsas, consolida cpf/e-mail/formação/ativo e remove os duplicados. Retorna o número de bolsas movidas. Loga em `scholarship_audit` (`action='merge_holders'`).
- `delete_holder_cascade(p_holder_id uuid) → integer` — exclui um bolsista e todas as suas bolsas numa transação. Usado pela tela de Bolsistas após confirmação explícita. Retorna o número de bolsas removidas.
- `save_user_assignments(p_user_id uuid, p_role text, p_project_ids uuid[])` — **admin-only** (security definer + guard `is_admin()`). Atualiza o papel em `app_users` e reescreve `user_projects` (delete + insert dos IDs passados) numa transação. Usada pela página Usuários & Centros de Custo.
- `get_saldo_livre(p_project_id uuid) → jsonb` — saldo realmente livre por grupo de rubrica até o fim da vigência: `previsto − realizado − compromissos de bolsas`. Retorna `{ has_plano, has_balancete, end_date, meses_restantes, data_referencia, balancete_defasagem_meses, saldo_disponivel_caixa, compromissos_inicio, compromissos_fim, compromissos_bolsas, bolsas_ativas: [{bolsista, valor_mensal, end_date, meses, compromisso}], grupos: [{grupo_code, grupo_name, previsto, realizado, saldo, compromissos, saldo_livre, compromissos_cobertura}], rubricas: [...], avisos: [], nota }`. `grupos` é a superfície de decisão; `rubricas` é o detalhe. `security definer` + guard `assert_project_allowed`. Não retorna CPF.
- `simular_alocacao(p_tipo text, p_valor numeric, p_rubrica text, p_inicio date, p_meses int, p_project_ids uuid[]) → jsonb` — onde cabe uma bolsa (`p_tipo='bolsa'`, recorrente) ou uma compra (`'compra'`, pontual), entre os centros de custo visíveis ao chamador. Retorna `{ nota, resumo: { cabe, cabe_parcial, nao_cabe, sem_plano, elegiveis, mais_urgente, mais_urgente_veredito, observacao }, projetos: [{ posicao, project_id, project_name, project_code, veredito, motivo_codigo, motivos, prioridade, valor_cabivel, meses_cabiveis, meses_solicitados, orcamento, caixa, prazo, remanejamento, risco_devolucao, avisos }], parametros, projetos_avaliados, gerado_em }`. Veredito é `cabe` | `cabe_parcial` | `nao_cabe` | `sem_plano`. `security invoker`. Não retorna CPF. Consumida pelo servidor MCP (`mcp/`) e, futuramente, pela aba de assistente do site.
- `get_panorama(p_project_ids uuid[], p_incluir_inativos boolean) → jsonb` — visão consolidada de todos os centros de custo visíveis ao chamador. Retorna `{ gerado_em, filtro, resumo: { centros, com_plano, sem_plano, sem_balancete, balancete_defasado, balancete_em_dia, balancete_desconhecido, vigencia_encerrando, com_alertas, alertas_graves, saldo_livre_total, custo_mensal_total, bolsas_ativas_total, observacao }, centros: [{ project_id, project_name, project_code, ativo, end_date, meses_restantes, vigencia_encerrando, situacao_dado, saldo_livre, grupos, caixa: { saldo_disponivel, data_referencia, defasagem_meses, cobertura }, bolsas: { ativas, custo_mensal, compromissos_ate_fim_vigencia }, total_desembolsado, alertas: { total, graves, itens }, avisos }], nota }`. `situacao_dado` é `completo` | `sem_balancete` | `sem_plano`; `caixa.cobertura` é `atualizada` | `defasada` | `nenhuma` | `desconhecida`. Os quatro estados de cobertura são mutuamente exclusivos e devem somar `resumo.centros`. **Ordem alfabética — não é ranking** (para urgência, use `simular_alocacao`). `sem_plano` devolve `saldo_livre` **null, não zero**. `security invoker`. Não retorna CPF, mas **retorna nome de bolsista** dentro das mensagens de alerta (é o conteúdo do alerta). Consumida pelo servidor MCP (tool `panorama`).

> **Hardening de RPCs (mig. 033 + 034):** `calc_project_monthly`, `calc_projects_batch`, `calc_general_dashboard` e `monitoramento_stats` são `security invoker` (o RLS auto-escopa as leituras internas). `get_plano_ativo`, `get_planos_historico`, `get_balancetes_by_project`, `get_previsto_vs_realizado`, `get_balancete_detalhado`, `upsert_plano_trabalho`, `ativar_plano_trabalho` e `upsert_balancete` mantêm `security definer` + guard `assert_project_allowed(p_project_id)`. **Desde a mig. 034**, `save_project` e `apply_reconciliation` passam a `security definer` + guard **escopado** (admin OU professor dono do projeto; `apply_reconciliation` ainda escopa as mutações de holder pelo predicado `is_admin() or created_by = auth.uid() or exists(bolsa no p_project_id)`); `merge_holders` e `save_user_assignments` mantêm `security definer` + guard admin-only. **Desde a mig. 038**, `get_saldo_livre` entra no grupo `security definer` + guard `assert_project_allowed(p_project_id)` (precisa ler `plano_rubricas`/`balancete_lancamentos`, admin-only no RLS), com EXECUTE revogado de `public`/`anon` e concedido só a `authenticated` — a mig. 035 fez funções novas nascerem fechadas, então o grant é explícito. **Desde a mig. 040**, `get_panorama` entra no grupo `security invoker` (mesmo critério da 039), com EXECUTE revogado de `public`/`anon` e concedido só a `authenticated`. As demais (`save_editor_changes`, `upsert_project_balance`, `get_balances_for_month`, `get_project_alerts`, `get_alerts_for_projects`, `funding_stats`, `delete_holder_cascade`, `resolve_rubrica_for_conta`, `fmt_month_pt`, `generate_month_series`) já eram `security invoker` e o RLS as escopa — **atributo que vem da mig. 019**, não da 033. Isso importa na hora de auditar: a 019 fez um lote grande de `ALTER FUNCTION ... SECURITY INVOKER`, as 021/025/026 desfizeram algumas ao recriá-las com `create or replace` (que substitui SECURITY e SET junto com o corpo — lição da 036), e a 033/036 reaplicaram nas que precisavam. **Ler só uma migração leva à conclusão errada**; a fonte de verdade é o banco:
>
> ```sql
> select proname, prosecdef, proconfig
>   from pg_proc p join pg_namespace n on n.oid = p.pronamespace
>  where n.nspname = 'public' and proname in (...);
> ```
