# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Financial control system for LAPIG (Laboratório de Processamento de Imagens e Geoprocessamento / UFG). Migrated from Google Sheets + Apps Script to a Vanilla JS + Supabase web app. The entire UI and documentation are in **Brazilian Portuguese (pt-BR)**.

## Running the App

No build step. Serve `frontend/` with any static file server:
```bash
cd frontend && python -m http.server 8080
```
Or use `abrir-site.bat` in the project root. **Must use HTTP** — `file://` breaks `<script type="module">` (pure-fns.js). Supabase credentials live in `frontend/js/supabase-config.js`.

## Dev Tooling

The frontend has no build step — all JS loads via `<script>` tags. For linting, testing, and CI, the project uses Node.js:
```bash
npm ci          # install dev dependencies (eslint, vitest)
npm run lint    # run ESLint on frontend/js/
npm test        # run Vitest on tests/
```

CI runs on GitHub Actions (`.github/workflows/ci.yml`) on push/PR to main/master.

Migration `035_lockdown_anon.sql` fecha o role **`anon`** antes da publicação. Brecha encontrada na auditoria: `create function` concede EXECUTE a `PUBLIC` por padrão e o PostgREST expõe o schema `public` como RPC ao `anon` — e `security definer` **burla o RLS**. Das ~25 funções definer, só 4 tinham `revoke ... from anon` (mig. 033); as demais só se salvavam pelo guard interno `assert_project_allowed()` (que levanta exceção para `anon`, pois `is_admin()` é false e `allowed_project_ids()` é vazio) — sorte estrutural, não garantia. `resolve_rubrica_for_conta(text)` (mig. 026) era definer **sem guard** e chamável sem login. A migração revoga EXECUTE de `public`/`anon` em todo o schema, devolve a `authenticated`, e usa `alter default privileges` para que **funções futuras já nasçam fechadas** (sem isso, a próxima migração reabre a brecha). `rls_auto_enable()` continua revogada também de `authenticated`; `resolve_rubrica_for_conta` mantém `authenticated` de propósito (é chamada pelo trigger invoker `auto_resolve_rubrica_lancamento`, e um usuário logado já lê `conta_rubrica_map` direto). Os grants de SELECT do `anon` nas **tabelas** ficam intactos — ali a barreira é o RLS (verificado: 20/20 tabelas com RLS, zero policies `to anon`/`to public`), e manter o SELECT deixa o keep-alive do n8n receber 200 + `[]` em vez de 401. Termina com um bloco `do $$` de **asserção** que aborta se houver tabela sem RLS, policy alcançável por `anon`, função executável por `anon` ou bucket público — reexecutável a qualquer momento como reauditoria.

Migration `036_search_path_hardening.sql` fixa `set search_path = public, pg_temp` nas 5 funções vivas que ficaram sem ele (3 delas `security definer`): `update_updated_at`, `sync_project_balance`, `enforce_single_plano_ativo`, `resolve_rubrica_for_conta`, `auto_resolve_rubrica_lancamento`. Sem search_path explícito o `pg_temp` entra implicitamente na frente do caminho de busca e permite sombrear chamadas não qualificadas dentro de funções definer (lint 0011 do Supabase). **Não era explorável pela web** — o PostgREST não expõe SQL arbitrário, então não há como criar o objeto temporário pela API; é defesa em profundidade. Registra a causa da regressão: a migração 019 já havia corrigido `sync_project_balance` via `ALTER`, mas a **021 recriou a função com `create or replace`, que substitui a definição inteira — incluindo os atributos SET e SECURITY** — e desfez a correção silenciosamente (mesmo padrão em 025/026). Regra: `set search_path` faz parte do corpo da função, não é ajuste externo. Termina com asserção que aborta se sobrar qualquer função (não pertencente a extensão) sem search_path.

Migration `037_linter_hardening.sql` resolve os warnings remanescentes do Supabase Database Linter pós-publicação. (A) `rls_policy_always_true` em `rubricas` (INSERT/UPDATE/DELETE) e `conta_rubrica_map` (INSERT/UPDATE): ambas são catálogos **globais** (sem `project_id`, impossíveis de escopar com `allowed_project_ids()`), e o frontend **nunca** escreve direto nelas — o dropdown de rubricas é a constante JS `RUBRICAS` (`plano-trabalho.js:39`), e novos mapeamentos conta→rubrica são gravados pela RPC `upsert_balancete` (security definer, bypassa RLS). Logo as policies de escrita `(true)` para `authenticated` não têm consumidor legítimo pelo PostgREST; foram endurecidas para admin-only (`is_admin()`). SELECT fica `(true)` (dado de referência sem PII — o linter não flaga SELECT). O fluxo do professor (salvar mapeamento na revisão do balancete) é preservado: roda via `upsert_balancete` (definer), que bypassa RLS. (B) `authenticated_security_definer_function_executable` em 6 funções que **não** são RPC expostos ao frontend: revoga EXECUTE de `authenticated` (anon já revogado na 035) nos 5 triggers `audit_trigger_function`, `enforce_single_plano_ativo`, `handle_new_user`, `set_holder_created_by`, `sync_project_balance` (triggers disparam sem checar EXECUTE do chamador — continuam funcionando, só deixam de ser chamáveis como `/rpc/...`) e no helper `assert_project_allowed` (chamado só dentro de outras RPCs definer, que rodam como o dono com EXECUTE). **Mantêm** EXECUTE em `authenticated` (intencional, warning benigno): `is_admin`/`allowed_project_ids` (chamados pelas policies de RLS), `resolve_rubrica_for_conta` (chamada pelo trigger invoker `auto_resolve_rubrica_lancamento`) e as 12 RPCs definer do frontend (cada uma com guard interno `assert_project_allowed`/`is_admin` que o linter não enxerga). Termina com asserção reauditoria que aborta se alguma das 6 funções ainda for executável por `authenticated` ou se sobrar policy permissiva de escrita nos catálogos. O warning `auth_leaked_password_protection` (Leaked Password Protection disabled) **não é SQL** — habilitar no Dashboard: Authentication → Sign in → Passwords → "Leaked password protection".

Migration `038_saldo_livre.sql` adiciona a RPC `get_saldo_livre(p_project_id)` — primeira peça da camada de **decisão** (as demais RPCs são de leitura/cadastro). O sistema já respondia "quanto sobrou?" olhando para trás (`get_previsto_vs_realizado`: plano ativo × balancete mais recente) e "quanto sai por mês?" olhando para frente (`calc_project_monthly`: bolsas ativas mês a mês), mas nunca cruzava as duas — e é o cruzamento que decide se cabe uma bolsa nova ou a compra de um equipamento: `saldo_livre = previsto − realizado − compromissos assumidos até o fim da vigência`. Sem descontar os compromissos, o saldo do balancete parece maior do que é (as bolsas ativas continuam sendo pagas todo mês até o fim da vigência). Decisões de semântica, todas documentadas no cabeçalho da migração: (a) compromissos contam a partir do mês **seguinte** ao `data_referencia` do balancete — o anterior já está no `realizado`, e contar de novo seria dupla contagem; balancete atrasado torna o resultado conservador de propósito (empurra para "cabe menos", o lado seguro), com o atraso exposto em `balancete_defasagem_meses`; (b) a superfície de decisão é `grupos` (rollup por `coalesce(parent_code, code)`), não `rubricas` — o plano PROAD ora orça na letra-mãe (`a — Pessoal`), ora nas sub-rubricas, enquanto o balancete sempre resolve na sub-rubrica, e comparar código a código produz saldo negativo quando o plano orçou só na mãe (validado: caso real dá −20.000 por rubrica vs. +45.000 por grupo); (c) só compromissos de **bolsas** são rastreados (não há previsão de contrato/diária/equipamento em nenhuma tabela), então cada grupo devolve `compromissos_cobertura` (`'bolsas'` | `'nenhuma'`) — distinguir "zero compromissos" de "compromissos não rastreados" é requisito, não detalhe, para quem lê o retorno (pessoa ou IA) não tomar `saldo_livre` por verificado; (d) **não** decide remanejamento entre letras (exige aprovação do financiador). `security definer` + guard `assert_project_allowed` (precisa ler `plano_rubricas`/`balancete_lancamentos`, admin-only no RLS desde a 033); não retorna CPF. Roteiro de conferência em `tests/sql/test_saldo_livre.sql` — cada bloco é autossuficiente (`begin; set_config; query; commit;`) porque o SQL Editor do Supabase **não** preserva `set_config` entre execuções separadas.

Migration `039_simular_alocacao.sql` adiciona a RPC `simular_alocacao(p_tipo, p_valor, p_rubrica, p_inicio, p_meses, p_project_ids)` — segunda peça da camada de decisão. A 038 responde "quanto está livre **neste** centro de custo?"; a 039 responde a pergunta comparativa que motivou a camada ("onde é melhor colocar uma bolsa de R$ 2.000/mês?"), rodando `get_saldo_livre` em todos os centros de custo visíveis ao chamador e devolvendo lista **ranqueada** com veredito e justificativa. Não redefine nada — herda a semântica já conferida da 038. **É shortlist com justificativa, não decisão:** ordena por urgência de gasto (qual recurso some primeiro se ninguém gastar) e **não julga mérito** — se aquele bolsista se justifica dentro do objeto daquele projeto (vínculo temático, plano de trabalho da pessoa, defesa perante o financiador) não existe em tabela alguma e é decisão humana. Por isso o resumo diz `mais_urgente`, nunca "melhor", e a `nota` instrui quem consome (tela ou IA) a **expor as opções com o porquê de cada uma, não afirmar recomendação**. Consequência para validação: escolher uma posição mais abaixo por razão temática é uso correto; o erro que importa é o **falso negativo** (opção viável fora da lista ou marcada `nao_cabe` sem ser). Validada contra uma **réplica local do banco real** (dump via `supabase db dump`, sem as tabelas com PII, restaurado em container): zero falso negativo nos `nao_cabe`, escopo por professor exato. A validação expôs um **viés do ranking**: sem balancete o `realizado` é zero *por ausência de dado*, o `saldo_livre` vira o previsto integral do plano e o centro de custo sobe ao topo — nos dados reais, as duas primeiras posições eram justamente os dois únicos sem balancete. Daí `risco_devolucao.base` (`balancete` | `apenas_plano`) e um alerta em `resumo.observacao` quando algum dos 3 primeiros é `apenas_plano`: o projeto **não** é suprimido (isso seria o falso negativo), mas a ordem passa a declarar que está sendo produzida por falta de dado. Decisões, todas no cabeçalho da migração: (a) **três restrições independentes**, porque tratá-las como um número só esconde o motivo do "não" — orçamento (saldo livre do grupo alvo), **caixa** (regra do coordenador: bolsa só se paga com dinheiro em conta, então há projeção **mês a mês** do balancete até o fim da vigência, com entradas de `plano_desembolsos` posteriores ao balancete e saídas das bolsas ativas) e prazo (vigência, que gera `cabe_parcial` — "cabe, mas só 5 dos 24 meses"); (b) as **direções de erro são opostas** e isso é dito em toda resposta — o orçamento é conservador (compromissos descontados, herdado da 038) e o caixa é otimista, pois a única saída que o banco sabe **prever** é bolsa. Mas o otimismo do caixa não é buraco permanente, e a distinção decide quanto confiar no número: são **duas lacunas** com remédios diferentes. A **retrospectiva** (o que já saiu e ainda não foi visto) é limitada, porque o ponto de partida da projeção é o `saldo_disponivel` do balancete — saldo real da conta, que já embute diária/equipamento/contrato pagos até a `data_referencia`; a cegueira vale só de lá até hoje e sai quantificada em `caixa.janela_cega_meses` (`caixa.cobertura`: `atualizada` até 2 meses — regime normal dado o atraso de emissão da FUNAPE, mesmo limiar de alarme da 038 —, `defasada` acima, `nenhuma` sem balancete). **É a rotina do Fechamento Mensal que mantém essa janela pequena: a qualidade da decisão é função direta de o balancete estar em dia.** A **prospectiva** (gasto não-bolsa futuro que ninguém orçou) é estrutural e o balancete não fecha, por ser retrospectivo — o que a rotina mensal dá ali é **detecção**, não previsão: o saldo do mês seguinte revela o quanto de fato saiu e a simulação se refaz. Cada item traz ainda `motivo_codigo` (`prazo`/`caixa`/`orcamento`/`sem_rubrica_pessoal`/`sem_plano_ativo`) — qual restrição está amarrando, em campo legível por máquina — e **todos os itens têm o mesmo conjunto de chaves**, inclusive os de curto-circuito, para o MCP e a tela iterarem sem checar forma; (c) **remanejamento é atrito de processo, não veredito**: toda implementação de bolsa exige remanejamento haja ou não saldo na letra de pessoal, porque é o ato que **nomeia o bolsista** — usá-lo como critério de ranking ordenaria por uma característica que todos compartilham; os graus são `nomeacao` (há saldo em pessoal), `entre_letras` (verba vem de outra letra — possível, mas custa tempo e desgaste) e `nenhum` (compra com espaço na rubrica). O **único** portão que remanejar não contorna é o plano não ter nenhuma rubrica do grupo `a` (`nao_cabe`, `motivo_codigo = 'sem_rubrica_pessoal'`); (d) o ranking é por **risco de devolução**, não volume: `prioridade = saldo_livre_realocavel / meses_restantes` (taxa de queima necessária para não devolver) — R$ 30 mil vencendo em 4 meses ganha de R$ 200 mil com 3 anos pela frente; (e) `cabe` e `cabe_parcial` compartilham o mesmo balde de ranking **de propósito** — separá-los inverteria a regra (d) exatamente no caso que ela existe para resolver; só `nao_cabe`/`sem_plano` caem para o fim; (f) pool remanejável exclui `cip_ufg`/`cip_ua`/`dao` (fatia institucional) e grupos com saldo negativo. `security invoker` (ao contrário da 038): tudo que lê direto já é escopado por RLS desde a 033, e o dado admin-only chega pela `get_saldo_livre`, que é definer **e** guardada. Roteiro de conferência em `tests/sql/test_simular_alocacao.sql`, mesmo idioma autossuficiente da 038.

Migração `040_panorama.sql` faz duas coisas. **(A) Repara `get_project_alerts`, quebrada em runtime desde a 032.** Descoberto ao rodar o `get_panorama` pela primeira vez contra a réplica do banco real: a função explode com `relation "public.expenses" does not exist`. O corpo vivo no banco é o da migração **003**, que tem um quarto alerta (`expense_no_description`) lendo `public.expenses`; a 032 dropou essa tabela **e** recriou a função sem esse alerta — a seção 4.5, cujo próprio comentário diz "sem recriar a função, ela — e `get_alerts_for_projects` (013), que a chama — quebraria em runtime após o drop da tabela". O drop chegou ao banco; a recriação, não. Evidência de que é o corpo da 003: `monitoramento` existe e `expenses` não (logo a 032 rodou), o corpo menciona `expense_no_description`, e os atributos são `security invoker` + `search_path`, que a 003 não tinha (era definer) e a **019** aplicou por `ALTER` — ou seja 003 + 019, sem a 032. Plpgsql só resolve nome de tabela em tempo de **execução**, por isso a função foi criada sem erro e só falha quando alguém pede alerta: os alertas da página Projetos (`projetos.js:138`) e o sino do Dashboard (`dashboard.js:213`, via `get_alerts_for_projects`) estão quebrados desde então. A 040 reaplica textualmente a versão da 032 — não é feature nova — e vai nesta migração, e não numa própria, porque o `get_panorama` chama essa função e não roda sem ela. (Registro de um beco sem saída da investigação: `get_alerts_for_projects` e `funding_stats` **não** têm problema de escopo — a **019** já as converteu para `security invoker` nas linhas 62–68, e o `alter function` da 033 nas 4 RPCs de cálculo era *reaplicação* do que a 019 fizera e as 021/025/026 haviam desfeito com `create or replace`. Grepar só a 033 leva à conclusão errada de que ficaram definer.) **(B) Cria `get_panorama(p_project_ids, p_incluir_inativos)`**, a pergunta que vinha antes das outras duas e não tinha resposta: a 038 responde "quanto está livre neste centro?" e a 039 "onde colocar este gasto?", mas "como estão os projetos?" exigia N chamadas e consolidação mental — e, pior, exigia saber de antemão o que perguntar (quem não sabe que um balancete está seis meses atrasado não vai conferir justamente o centro cujo número menos merece confiança). Decisões: (a) **panorama descreve, não ranqueia** — ordem alfabética, sem significado; ranquear é da 039, que parte de uma hipótese concreta de gasto, e um segundo ranking aqui usaria outro critério e produziria duas listas "de prioridade" discordantes; a `nota` diz isso para tela e IA não inventarem urgência a partir de descrição; (b) **não recalcula nada** — todo número vem de `get_saldo_livre`, `get_project_alerts` ou da view `v_project_summary`, e o único cálculo local é somar os `saldo_livre` dos grupos que a 038 já devolveu; (c) **a qualidade do dado é parte da resposta**: cada centro traz `situacao_dado` (`completo`/`sem_balancete`/`sem_plano`) e `caixa.cobertura`, porque saldo alto sem balancete é previsto integral com realizado zero por ausência de dado — balancete ausente **superestima**, balancete defasado **subestima**, direções opostas que não se cancelam; `sem_plano` devolve `saldo_livre` **null, não zero**; (d) o limiar de `cobertura` é o **mesmo da 039** (até 2 meses `atualizada`), para panorama e simulação serem lidos lado a lado sem traduzir, mais um quarto estado que não existe na 039: **`desconhecida`**, quando o centro não tem plano ativo — nesse caminho a 038 devolve o objeto curto, que traz `has_balancete` mas **não** `data_referencia` nem `balancete_defasagem_meses` (ela consultou os dois, só não os inclui ali), e sem esse ramo o `coalesce(defasagem, 0) <= 2` leria o NULL como zero e declararia "em dia" um balancete de idade desconhecida. O conserto de raiz é a 038 carregar esse contexto no caminho curto; enquanto isso, o quarto estado diz a verdade. Os quatro estados são mutuamente exclusivos e o resumo os conta separadamente — devem somar `centros`. `resumo.sem_balancete` + `resumo.balancete_defasado` são a **leitura de saúde do Fechamento Mensal** — até aqui não havia como ver numa consulta quais centros estavam com o dado atrasado. `security invoker` pelo mesmo critério da 039. Roteiro em `tests/sql/test_panorama.sql`, que inclui a demonstração do furo (rodar o bloco 1.a **antes** de aplicar a 040 é o único jeito de vê-lo existir antes de vê-lo fechado).

## Key Conventions

- **No frontend build step.** All JS is browser-native ES5/ES6 loaded via `<script>` tags, except `pure-fns.js` which loads as `<script type="module">` and bridges exports to `window` for classic scripts. Dev tooling (eslint, vitest) runs via Node.js (`package.json`).
- **Conventional commits:** `feat:`, `fix:`, `chore:`, `docs:` prefixes.
- **CSS design system:** `frontend/css/style.css` (~1760 lines) uses CSS custom properties for theming. LAPIG institutional colors, glassmorphism effects.
- **CDN with local fallback:** Libraries (Chart.js, Lucide, Supabase SDK, Mammoth, pdf.js, SheetJS) load from CDN with SRI integrity hashes. If CDN fails, `frontend/vendor/` provides local copies.
- **Keep-alive do Supabase via n8n:** `n8n-keep-alive-lapig.json` (workflow) + `N8N_KEEP_ALIVE_SETUP.md` (guia) evitam que o projeto gratuito do Supabase entre em pausa por inatividade (7 dias). A cada 2 dias, o workflow faz uma query de leitura idêntica à da landing page (`projects` ativos). Não altera dados.
- **Security:** CSP meta tag in `index.html`. Sentry integration in `supabase-config.js` for error monitoring.
- **Multi-tenancy por centro de custo (mig. 033 + 034):** cada usuário autenticado tem um papel (`admin`/`professor`) em `app_users` e centros de custo permitidos em `user_projects`. `auth.js` carrega o perfil no login (`Auth.isAdmin()`/`getRole()`/`getAllowedProjectIds()`) **antes** de `App.init()`. Professores veem/editam só os seus projetos — o RLS escopa todos os `from('projects')`, as views `security_invoker` e as RPCs invoker; admins veem tudo. **Desde a mig. 034 o professor também gerencia projetos** (cria — auto-atribuído a si em `user_projects` — e edita os seus via `save_project`) **e roda o Fechamento Mensal** (checklist escopado + reconciliação de bolsas via `apply_reconciliation` escopado); a mescla de duplicados (`merge_holders`, global) e a gestão de usuários (`save_user_assignments`) continuam admin-only. Só a rota **Usuários & Centros de Custo** (`usuarios.js`) tem `data-admin` no `<li>` (oculta no sidebar) + guard em `app.js` (Fechamento e Gestão de Projetos agora são professor-acessíveis). Criar logins continua no painel do Supabase (signup desativado); a anon key é pública, então o RLS é a barreira real — a service_role key **nunca** vai no frontend.
- **localStorage keys** use `cf_` prefix: `cf_selected_project_id`, `cf_dashboard_selected_projects`, `cf_plano_trabalho_project_id`, `cf_plano_trabalho_tab`, `cf_holders_tab`. (`cf_recon_project_id` foi aposentada — o projeto da reconciliação agora é escolhido por arquivo na fila de importação.)
- **Navegação com mudanças não salvas:** o `Router` expõe `registerGuard(fn)` e `registerDirtyChecker(fn)` (consumidos por `projetos.js` e `saldos.js`); `hasUnsavedChanges()` alimenta o `beforeunload` em `app.js` que avisa ao fechar/recarregar a aba. Mudanças não salvas no modo editor (Projetos) e nos saldos pendentes (Saldos) pedem confirmação antes de trocar de rota.
- **Edge Functions** ficam em `supabase/functions/`. Ambas (`extract-plano-trabalho` e `extract-balancete`) eram proxies Ollama Cloud (`kimi-k2.6:cloud`) e estão **deprecated** desde 2026-05. O frontend não chama mais nenhuma — a extração é 100% determinística: `frontend/js/parsers/balancete-parser.js` (PDF→regex) e `frontend/js/parsers/pt-parser.js` (DOCX→mammoth→HTML→parser). As funções permanecem deployadas como histórico. Deploy manual via `supabase functions deploy <name>`. Secret `OLLAMA_API_KEY` continua configurado mas não é mais consumido em runtime.
- **Servidor MCP** fica em `mcp/` (pacote Node próprio, `type: module`, sem relação com o frontend sem build). É a **fase 2** da camada de IA — adaptador fino sobre as RPCs de decisão das migrações 038/039, com uma regra dura: **zero lógica financeira no adaptador**, porque a fase 3 (aba no site) vai consumir as mesmas RPCs e duas implementações da mesma conta divergiriam. Autentica **por usuário** (`CF_EMAIL`/`CF_PASSWORD` no bloco `env` do cliente MCP): faz login de verdade no GoTrue e chama as RPCs com o JWT daquele usuário, então o RLS das migrações 033/034 é a barreira e o servidor não tem lógica de permissão própria. Tools (9): `listar_centros_de_custo`, `panorama`, `saldo_livre`, `simular_alocacao`, `consultar_bolsas` (colunas explícitas — CPF e e-mail nunca saem), `previsto_vs_realizado`, `projecao_de_caixa`, `plano_de_trabalho` e `quem_sou_eu`. As descrições das tools carregam o enquadramento das migrações porque é o que o modelo lê (shortlist com justificativa, não recomendação; declarar o que o número cobre; **`panorama` descreve e `simular_alocacao` ranqueia** — a ordem do panorama é alfabética e não é prioridade). As tools de leitura declaram o que **não** cobrem: `previsto_vs_realizado` só olha para trás, `projecao_de_caixa` só sabe prever bolsa e parte do saldo cadastrado no projeto (não do balancete), `plano_de_trabalho` é o orçado e não o executado. **Não existe tool `alertas` separada** de propósito: o `panorama` já traz os alertas de cada centro, e duas portas para o mesmo dado é o começo da inflação de tools que degrada a escolha do modelo. `panorama` exige a migração 040; as demais, as 038/039. Transporte stdio: **nada** em stdout além do protocolo — log vai para stderr. Conferência: `npm run smoke` sobe o servidor como cliente MCP real e exercita as tools ponta a ponta; rodar com os dois logins (professor e admin), porque um resultado vazio pode ser correto e ainda assim esconder que a conferência passou a vazio.
- **Ambientes de teste local do banco** ficam em `tools/replica-local/` (README com as receitas): nível sintético (5 centros de custo, um por restrição, sem credencial), réplica do banco real raspada de PII (container `cf-real`) e a **stack Supabase local** (`supabase/config.toml` versionado, só db+auth+rest ligados). Só a stack completa testa o que os adaptadores podem errar — grant a `authenticated`, exposição de RPC, parsing de JWT e tradução de erro; Postgres puro valida cálculo, não transporte. Dumps nunca são versionados (`tools/replica-local/dump/` no `.gitignore`).
- **Parsers e componentes determinísticos** ficam em `frontend/js/parsers/` (balancete + plano de trabalho em DOCX e em PDF + tabela de aliases de rubrica + detector de modelo de plano + planilha de bolsas FUNAPE) e `frontend/js/components/` (split-views PDF e DOCX). O plano PROAD tem **dois** parsers porque o pdf.js não entrega estrutura de tabela: `pt-parser.js` (DOCX→mammoth→`<table>`) e `pt-pdf-parser.js` (PDF→pdf.js→linhas, com o total declarado de cada letra como árbitro sobre as folhas — ver `docs/planos-fora-do-padrao.md`). São módulos ES carregados via `<script type="module">` no `index.html` e bridge-ados ao `window` para uso pelos scripts clássicos. `bolsa-parser.js` lê XLSX via **SheetJS** (`window.XLSX`, CDN `xlsx@0.18.5` + fallback em `frontend/vendor/xlsx.full.min.js`) e devolve `{ data, warnings }`; `bolsa-comparator.js` compara planilha × banco e devolve `{ novos, removidos, alterados, iguais }` (com `matchKind` `link`/`new` e `existingHolderId` para evitar duplicados globais).
- **Página "Visão do Projeto" (`hub.js`)** é uma tela agregadora **experimental** (somente leitura) que reúne os 4 KPIs-chave de um projeto e atalhos "Abrir" para cada área. Compartilha o projeto selecionado com a aba Projetos (`cf_selected_project_id`). Registrada no `Router` como `hub` e no sidebar com ícone `telescope`.
- **Fila de importação genérica (`frontend/js/import-queue.js`)** — componente global `ImportQueue` (classic script) com o contrato de handler documentado no cabeçalho do arquivo. Handlers existentes: plano DOCX e balancete PDF (`PlanoTrabalhoPage.getImportHandlers()`) e bolsas XLSX (`HoldersPage.getBolsaImportHandler()`). A página **Fechamento Mensal** (`fechamento.js`, rota `fechamento`) abre a fila com os 3 handlers de uma vez (roteamento por extensão) e mostra o checklist da competência: projetos FUNAPE ativos × balancete recebido × planilha de bolsas conferida × plano ativo. Três pontos do contrato existem para os **planos fora do padrão** (ver `docs/planos-fora-do-padrao.md`): `fallbackExt(name)` reivindica formatos sem leitor automático só quando nenhum handler os quis por `validExt` (impede o handler de plano de roubar o XLSX de bolsas no Fechamento); um erro de `parse` com `.rerouteTo = '<type>'` reentrega o arquivo a outro handler — é assim que um **PDF de plano** roteado como balancete volta para o handler de plano; e `manualFallback(file)` faz a tela de erro oferecer **"Preencher manualmente"** em vez de só "Pular", reaproveitando o formulário de revisão (que já é editor completo) com o arquivo original anexado como comprovante.
- **Sidebar em seções** (`index.html` + `.sidebar__section` no CSS): "Rotina Mensal" (Fechamento, Saldos), "Acompanhamento" (Projetos, Visão do Projeto, Plano de Trabalho, Visão Geral), "Cadastros" (Bolsistas, Gestão de Projetos, Usuários & Centros de Custo [admin], Desembolsos, Observações). Itens `data-admin` são ocultados para professores em `app.js` (o RLS é a barreira real; o sidebar é só UX) — desde a mig. 034 só **Usuários & Centros de Custo** é `data-admin` (Fechamento e Gestão de Projetos ficaram professor-acessíveis).
- **Publicação:** `.github/workflows/deploy.yml` publica `frontend/` no GitHub Pages (Settings → Pages → Source: GitHub Actions). **Antes de tornar o repo público**, cumprir o checklist de `docs/seguranca-publicacao.md` — em especial desativar signup no Supabase Auth (a anon key é pública; a proteção é signup fechado + RLS `to authenticated`).
- **All monetary values** are stored and calculated as numeric (no integer cents). Display uses `formatBRL()`.
- **Default landing page** is `projetos`, not dashboard (re-init cai em `saldos` se não houver rota corrente — ver `app.js:11,45`).
